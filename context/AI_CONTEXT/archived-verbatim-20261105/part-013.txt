## Summary
- 目标：用户未来在另一台 Mac 上，理论上只需要执行一个安装包，就能装好整套后台服务。
- 产品应拆成两层：
  - 产品层：你自己的 runtime 安装包，负责安装、启动、托管、升级、观测
  - 内核层：`weclaw` fork，只负责微信桥接本体
- 设计原则：用户只面对“一个安装包”，但代码层面必须把“产品层”和“桥接内核”分开，否则后续升级会越来越难。

原文摘录：
## 明确边界
- 产品层必须负责：
  - `launchd` 服务注册与托管
  - `guardian`、`scheduler`、`codex`、`claude`、`weclaw` 的编排
  - `Watchdog 自动化报告`
  - 日志、状态文件、故障降级、清理旧残留
  - 安装、升级、卸载
- `weclaw` fork 只负责：
  - 微信登录与凭据
  - 消息桥接
  - API server
  - 基础 CLI 能力
- 不应放进 `weclaw` fork 的内容：
  - `guardian` 逻辑
  - `scheduler` 逻辑
  - `launchd` 产品托管逻辑
  - 你的 Watchdog 报告与 failover 策略

## 安装模型
- 最终交付物是一个大包。
- 用户只执行一次，例如：
  - `bash install.sh`
  - 或一个 `.pkg`
- 这个安装包内部完成：
  - 安装 `weclaw-real`
  - 安装 runtime 脚本和二进制
  - 写入 `LaunchAgents`
  - 注册 `guardian/codex/claude/weclaw/repo-scheduler`
  - 清理历史残留
  - 启动服务
- 用户首次只额外做一件事：
  - `weclaw login` 扫码
- 之后由常驻服务接管，不需要再手工 `weclaw start`
