## Summary
- 把 Longclaw 重新定义成一个 `Self-improving personal agent system`，而不是“默认能长期后台主动给你发微信”的产品。
- 架构继续沿用四层：
  - `Client Runtime（端侧）`
  - `Agent Core（云侧）`
  - `Interaction Adapter Layer（通道侧）`
  - `Knowledge Review Plane（知识侧）`
- 新的关键现实约束必须写进产品定义：`weclaw / WeChat` 目前是 `windowed proactive messaging`，不是 `true background push`。
- 近期产品目标从“强行打通微信后台推送”改为“先把本地闭环做成可靠产品”，即：
  - WeChat 负责 ingress、实时会话、显式任务接入
  - Mac 负责可靠提醒、runtime host、自动化宿主
  - `Agent Core（云侧）` 方向先抽状态契约和 improvement loop，不急着先上云
- 产品路径改成三段：
  1. `Local Reliable Loop`
  2. `Portable Core Extraction`
  3. `Distributed Product Runtime`

## Key Changes
### 1. 重写产品承诺
- Longclaw 的主承诺改成：
  - 跨会话记忆
  - 双 agent failover
  - 可审阅知识沉淀
  - 任务排队与自动化迭代
  - `Harness Engineering Loop` 驱动的持续改进
- Longclaw 不再把“任意时刻稳定主动微信播报”作为当前版本承诺。
- `WeChat` 的正式能力边界改成：
  - 可靠：入站消息、会话内回复、`任务:` 入队、`/runtime` 或等价状态拉取
  - 条件性可靠：在最近 live context window 内的主动摘要
  - 不承诺：长时间空闲后的后台主动推送
- 可靠告警与状态交付默认转移到 `Client Runtime（端侧）`：
  - Dashboard
  - 本地通知
  - runtime state
  - review note
- 若未来需要真正 push，作为后续 `Delivery Channel` 能力建设处理，不继续让 WeChat 承担错误职责。

- `Knowledge Review Plane（知识侧）`
  - 继续做人类可读投影、审阅、干预、证据追踪
  - 不承担 machine canonical state

### 3. 把产品主链改成“Push Optional, Pull Reliable”
- 当前本地产品主链固定为：
  - `WeChat ingress`
  - `Routing Controller`
  - `Primary/Backup agent execution`
  - `Runtime state persistence`
  - `Knowledge projection`
  - `Runtime summary generation`
  - `Delivery policy`
- `Delivery policy` 明确三档：
  - `reply`: 对 live 会话即时回复
  - `windowed_proactive`: 仅在有效 WeChat context window 内发送摘要
  - `reliable_local`: 永远写 runtime state、dashboard、本地提醒
- 所有 scheduler 摘要、health alert、review signal 先写 `reliable_local`，再按条件尝试 `windowed_proactive`。
- 用户交互面增加明确的拉取式入口：
  - `任务: xxx`
  - `/runtime`
  - 后续可扩展 `/review`、`/queue`
- 这样产品体验从“赌后台 push”变成“状态永不丢，微信尽量快，必要时用户可主动拉取”。
