原文摘录：
1. **`automation_update` 是宿主控制面工具，不是 automation worker 内部能力**
   我在交互式 Codex 会话里能调用 `codex_app.automation_update`，因为这是 Desktop 宿主暴露给当前会话的工具。但 automation 后台子会话是一个独立任务运行环境，实际没有这个工具。prompt 里写“使用 automation_update”不会自动让它变成可调用工具；如果它当 shell 命令试，就会变成类似 `automation_update: command not found`。

来源：codex:019e0a63-f795-7721-93fb-d6d178e729c3#turn:019e0a6f-c0cb-7d60-9a19-af611a546e53
角色：assistant
性质：历史回复所报告结果（未作当前复验）
原文摘录：
2. **自修改调度状态本身容易和 scheduler 写状态竞争**
   automation 正在运行时，调度器同时要写 `last_run_at`、`next_run_at`、run status、inbox 状态。让任务在结束前改自己的 `status=PAUSED`，会出现先后顺序问题：任务以为暂停了，但 scheduler 可能已经算好下一次；或者 scheduler 最后写回覆盖一部分状态。平台通常会把“任务执行面”和“任务管理面”隔开，避免后台任务随意改自己或其他任务。

3. **分钟级 cron 不是 Codex automation 的强项**
   你这个 `a-5` 是 `FREQ=MINUTELY;INTERVAL=5`，又要求盘中高频运行、收盘补跑、然后自暂停。这类逻辑更像 daemon/state machine，不像智能任务。Codex automation 更适合“检查、解释、报告、失败归因”，不适合当 5 分钟生产调度器。
