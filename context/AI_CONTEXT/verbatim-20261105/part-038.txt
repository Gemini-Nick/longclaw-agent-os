## Summary
- 本轮所有工作只围绕两个目标收口：
  - `目标 1`：完成整体设计代码改造
  - `目标 2`：完成一次从 `WeClaw` 到客户端的完整验证
- 产品主线固定为：
  - `Chat launches, console governs.`
  - `Electron` 是唯一 default home
  - `WeClaw` 是 remote cowork companion
  - `Hermes` 是唯一 canonical `LaunchIntent -> Task / Run / Work Item` 编排层
- 能力调用策略固定为：
  - 前门以 **显性加载** 为主
  - 用户通过 `@pack / @skill / @plugin`、capability chips、presets、shortcuts 发起任务
  - 不把“自由文本智能猜 pack”作为本轮主目标
  - 当前已有的默认 pack / routing hint 只保留为兼容能力，不作为主 UX 或主验收路径

## Key Changes
### 1. 设计代码改造收口到产品层 + 运行时用户可见层
- `Electron` 信息架构最终锁定为：
  - `Home`
  - `Runs`
  - `Work Items`
  - `Packs`
  - `Studio`
- `Home` 必须彻底成为双层首页：
  - 左侧 `Cowork Launch`
  - 右侧 `Governance Snapshot`
- `Cowork Launch` 的完成标准固定为：
  - 支持自然语言输入
  - 支持显式 `@pack / @skill / @plugin`
  - 显示 active capabilities / recent launches / 当前 workspace context
  - 明确告诉用户：长时、evidence-heavy、needs-review 的工作会进入治理面
- `Studio` 的完成标准固定为：
  - 不做 marketplace 首页
  - 只展示 curated / visible capabilities
  - pack-first，skills/plugins 次之
  - 词表、状态、badge、detail drawer 语法与治理面完全一致
- `Runs / Work Items / Packs` 必须共享统一的 row/drawer/preview 语法，不允许页面各自发明第二套交互
- 运行时层本轮只改 **用户可见层**：
  - `install / apply-live / guardian / runtime status / weclaw bridge health / README / docs / 状态输出` 的命名、状态词、产品文案全部对齐 Longclaw 词表
  - 统一状态词：
    - `running`
    - `needs review`
    - `partial`
    - `delivery failed`
    - `degraded`
    - `reviewed insight`
  - 不在本轮改 `launchd / guardian / scheduler` 的深层内部契约和 state file shape

### 2. 前门与 canonical 编排收口
- `Hermes` 继续作为唯一 canonical 编排入口：
  - `POST /agent-os/launches`
  - `GET /agent-os/tasks`
  - `GET /agent-os/tasks/{task_id}`
- `LaunchIntent` 本轮冻结为前门唯一 canonical 输入对象
- `Electron Home` 和 `WeClaw` 都必须走同一条 Hermes launch 通路
- 主产品策略固定为：
  - canonical launch 依赖显式 capability loading
  - `@pack` 决定 pack
  - `@skill` 决定 workflow/preset
  - `@plugin` 决定 capability bundle / connector preset
- 兼容策略固定为：
  - 现有 `default launch pack / capability` 能力保留，但不作为主交互设计、不作为主验收路径
- `WeClaw` 的完成标准固定为：
  - 保持 channel semantics、消息/媒体解析、remote companion 定位
  - 不伪装控制台
  - 显式 capability launch 能提交 Hermes
  - 普通状态追问和轻量回复仍留在 WeChat 表面
- `Electron` 的完成标准固定为：
  - 最近 launches、tasks、capability substrate、治理状态在同一产品语言里可读
  - 不再让用户通过本地 cowork runtime 理解系统状态；状态归属始终落在治理面

### 3. 验证计划按“两条路径 + 两个交付物”收口
- 验证必须同时覆盖两条路径：
  - `模拟闭环`
  - `真实微信闭环`
- 验证交付形式固定为：
  - `模拟闭环 = 自动化`
  - `真实微信闭环 = 手工 runbook + 证据包`
- 验证矩阵固定为：
  - `模拟闭环` 以 `Due Diligence` 为主场景
    - 从 WeClaw 可控入口发起显式 capability launch
    - 经 Hermes 生成 canonical `Task / Run / Work Item`
    - 在 Electron `Home / Runs / Work Items / Packs` 中看到对应状态
  - `真实微信闭环` 以 `Signals Review` 为主场景
    - 在真实微信中发一条显式 capability 消息
    - 经 WeClaw 入站、Hermes launch、Electron 客户端看到对应 launch/task/run
- 为什么这样分配：
  - `Signals Review` 更适合作为真实微信演示路径
  - `Due Diligence` 更适合作为可控、可重复的模拟闭环验证路径
- 两条验证都必须输出证据：
  - Electron 截图
  - Hermes 任务/运行记录
  - WeClaw 日志或 API 调用记录
  - 失败时的排障路径
- 本轮验收不要求每个 pack 在每条路径都跑一遍；但合并后的验证矩阵必须覆盖：
  - 两条 ingress 路径
  - 两个 flagship pack
  - 一次 canonical task/run/work item 可见性

## Summary
- Longclaw 不再按“纯治理台”来定义，也不改成“聊天即产品”。新定位锁定为：**单人高杠杆操盘手的 Agent OS**。
- 产品结构采用 **双层并列**：
  - `Cowork Front Door`：负责发起任务、调用 `@plugin / @skill / @pack`、远程派单、轻量追问。
  - `Governance Console`：负责 `runs / artifacts / evidence / review / work items / delivery / promotion`。
- 设计方向继续锁定为 **Warm Industrial Command Center**，但保守吸收 `Claude Cowork / WorkBuddy / OpenHands` 这类产品的两个优点：
  - `能力可见性`
  - `发起体验`
- 借鉴策略明确为：**借结构，不借产品重心**。
  - 借：launch 输入条、active capabilities、context panel、能力提示、最近 launch 反馈
  - 不借：全屏聊天首页、紫色 AI SaaS 风、插件市场中心化、治理台降级
- 核心原则固定为：**`Chat launches, console governs.`**
