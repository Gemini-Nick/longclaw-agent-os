## 关键职责与现状
- `guardian.monitor`
  - 启动 `weclaw-guardian monitor --config ~/.weclaw/services.json --uid 501`
  - 作用是按 `services.json` 每 30 秒巡检 `codex.appserver`、`claude.worker`、`repo.scheduler`、`weclaw.bridge`，并执行保活/重启退避
  - 目前状态正常，主要是总控，不直接负责发微信
- `weclaw.bridge`
  - 通过 `weclaw-real start -f` 以前台方式被 `launchd` 常驻
  - 作用是维持本机微信桥接、监听本地端口 `18011`、承接 `weclaw send` 和任务派发 API
  - 目前“进程活着但上游不稳”，日志里有 `no such host`、`TLS handshake timeout`、`EOF`、`context deadline exceeded`
  - 在你要求下，必须继续工作在 TUN 模式，不能靠简单改成直连规避
- `claude.worker`
  - 当前实际走 `weclaw-guardian claude-worker`
  - 作用是 Claude 通道健康检查和备援能力维持，不参与微信摘要发送
  - 当前路由状态里 Claude 是 `not_logged_in`，因此只是备份不可用，不是本次微信送达失败的根因
- `codex.appserver`
  - 通过 `codex app-server --listen ws://127.0.0.1:45678`
  - 作用是给本地 runtime 暴露 Codex 服务能力，供主链路调用
  - 当前状态正常
- `repo.scheduler`
  - 每 4 小时执行一次 `repo-scheduler-service.sh`
  - 负责工作区扫描、cloud sync、dependency update、routing reconcile、harness tick、roadmap sync、wechat summary、queued task dispatch
  - “最近情况”就是它在生成，日志中可见它每轮都产出 `roadmap-queue.json` 和 `wechat-notification-state.json`
  - 当前真正的问题是：它生成了摘要，但发送逻辑被 delivery policy 阻断
